# Durable local publication positions

The position API in `internal/publicationstate` is an unwired, local-only library for a caller-supplied publication selection, bounded record evidence, a locally accepted position and explicit first-use/replacement consent. It is not provider transport or authentication. The future caller must authenticate account/session/repository membership, current policy and the supplied repository observation before calling this API. The origin binding is a caller-provided association, not proof: this package requires exact `Observation.Origin` equality with its immutable store binding before caching, preparing or accepting. Spaces and public-repository bindings are separate profiles and are never inferred from one another.

The position API is `Open(directory, binding)`, `OpenWithLimits(directory, binding, limits)`, `Close`, `Load`, `RecordObservation`, `Prepare`, `Accept` and bounded `History`. The Open entry points, including `OpenWithOptions`, accept no context and use `context.Background()` internally; they provide no caller-cancellation guarantee. The directory must already exist, be absolute, owned by the current user, and have mode `0700`. Existing lock/database/WAL/SHM objects must already be owned private regular files at `0600`; unsafe objects and hard links where detectable refuse before lock acquisition or SQLite. No path is discovered, directory is created, or permission is repaired. A mode=ro SQLite probe reads committed WAL schema metadata before a read-write connection is opened. The current library SQLite schema is 3: a new or valid initial empty database is created at schema 3, and a healthy current schema-3 database opens ordinarily whether the upgrade permissions are true or false. Ordinary `Open` refuses a recognized schema-1 or schema-2 store with `upgrade_required`; the probe is not a usable read-only store. Only `OpenWithOptions` with both `UpgradeFromPositions` and `UpgradeFromAttempts` enabled upgrades a genuine schema-1 position store directly to schema 3; a genuine schema-2 store requires `UpgradeFromAttempts` alone. Both permissions default to false, and enabled permissions on a new or current database cause no migration.

The upgrade validates the exact source schema, binding, limits and complete stored state before the migration transaction and revalidates them through the actual migration transaction. Before its first write, it also compares the source metadata exactly with the previously captured metadata; the probe and advisory lock are not substitutes for this transaction-local validation. Full source-state validation is distinct from the captured metadata comparison, not a byte snapshot comparison of every source row. A schema-1 upgrade adds the empty attempt tables and indexes, canonical `attempt_limits` and zero `attempt_mutation_revision` metadata, and the empty `accepted_material_refs` table. A schema-2 upgrade adds only the empty `accepted_material_refs` table. Both paths set SQLite `user_version` to 3 in the same migration transaction. Neither rewrites preserved source rows, counters, wire encodings or original limits: the database ID, binding, accepted floor, cache, raw accepted records and historical event encodings remain unchanged. No owner is inferred, no ownership row is backfilled and no candidate payload byte is written.

An upgrade Commit error or a post-Commit Open-completion failure returns a nil Store with `ErrStorage/open/commit_unknown`, requiring explicit reopen and readback; it does not prove rollback. Unknown or committed-with-error upgrade outcomes receive the same classification. Ordinary no-migration refusal classes are unchanged. Foreign, lookalike, active-v1, corrupt and future schemas are not adopted. The lock is advisory on this local filesystem. Malicious same-user namespace replacement and stronger path-opening guarantees are out of scope.

The database holds one immutable account/backend/repository/vault binding and creation-time limits. Reopening with another binding or limits refuses. There is no reset, accepted-history deletion, rebind, automatic migration, installed default path or active executable integration. SQLite uses one connection, a mutex and lifetime flock, WAL, FULL synchronous mode, foreign keys and a bounded busy timeout.

`Prepare` and `Accept` revalidate every supplied record and decode the candidate payload bytes with `publication.DecodePayload`; a prior valid marker never substitutes for those bytes. Payload bytes are not persisted by the position API. A stored floor and audit remain readable without the payload, but preparing/accepting again requires valid supplied payload bytes. Accepted history retains candidate-first descending ancestry references and the raw records needed to verify them; unused supplied records affect only the framed supplied-set digest. The position API does not claim complete repository membership, newest-position freshness, authorship, Spaces privacy, provider behavior, or authenticity.

The private compare-and-swap and consent digests use fixed ordered JSON wire DTOs, `[]byte` standard base64, UTF-8 validation, HTML escaping disabled and strict canonical round trips. They are internal store tokens, not a public or portable pin/confirmation protocol. `Floor.DatabaseID` and `Floor.Generation` must be consumed together as the invalidation pair `(DatabaseID, Generation)`: generation alone repeats after a new database is created. The v2 attempt layer consumes this pair for attempt eligibility and floor-replacement blocking; the service library also consumes it for process-local reconciliation-base eligibility, while durable v2 applied-base and journal integration remain unwired. Spaces remains unwired, and this package does not enable service cutover. See [offline local publication reconciliation](../service/README.md#offline-local-publication-reconciliation) for that separate service-library contract.

The accepted event log is append-only and has a default terminal cap of 8192 events. There is no hidden eviction, reset or new-directory recovery that preserves continuity. Once event count or accepted logical-byte capacity is exhausted, new first-use/advance/replacement events refuse with `ErrLimit/accept/capacity`; `Load`, `History` and fully validated same-position no-ops remain available. The cap is finite and is not an unlimited lifetime or guaranteed replacement reserve. The independent record-only cache has default limits of 4096 records, 1024 observations and 16 MiB logical bytes. Cache saturation refuses only cache intake and never inserts cache rows during `Accept` or gates authoritative capacity. Accepted storage separately caps 16384 unique records and 128 MiB logical bytes.

Logical accounting is deterministic. A cache or accepted record is `raw record byte length + CID byte length + key byte length + 8` for sequence metadata. An observation is its canonical metadata byte length plus 32 bytes for its ID and 8 bytes of row metadata. An event is canonical event-body length, event digest length, stored old/new floor encodings, mode/reason/stop text lengths and 8 bytes for its revision key. Accepted logical bytes sum accepted record and event accounting. History counts each canonical event-body length plus digest/revision metadata and each unique raw-record reference's record accounting once per page; it returns the largest complete prefix that fits 16 MiB without skipping an event. These are logical row/read bounds, not physical SQLite/WAL/index size, disk-space guarantees, RSS bounds or power-loss guarantees.

`Accept` atomically commits accepted raw records, complete event evidence, active floor, revision/generation and the historical payload-validation marker. It has no fallible post-success-commit check. A commit error is returned as `ErrStorage/<stage>/commit_unknown`, the live store refuses further preparation/writes until `Load` verifies persisted floor/audit state or the store is closed and reopened, and callers must read back rather than infer rollback. A successful marker is historical validation evidence, not payload availability. `Open`, `Load`, `Prepare`, `Accept` and `History` currently scan and revalidate the complete bounded accepted audit before proceeding; a History page caps returned event/evidence bytes, not total verification work. `HistoryEvent.Trace` references resolve through the page-level `HistoryPage.Records`, which deduplicates raw records by CID and includes each returned event's held old-floor record when present. Missing/corrupt accepted evidence refuses the page without partial results.

Errors expose only closed class/stage/reason metadata through formatting and unwrap. No raw SQLite/filesystem causes are returned. The position library stores sensitive position and repository/policy context; routine logs should use neither `Floor` nor `History` values.

## Offline publication attempts

The SQLite schema-3 attempt layer shares the local publication-state database and lock, and supports durable attempts, plaintext candidate custody and an empty incoming-reference table. SQLite schema version 3 is separate from the unchanged existing attempt encodings and the version-2 publication protocol. It does not replace the position API or wire transport. Its API is `OpenWithOptions`, `PrepareAttempt`, `CreateAttempt`, `ActiveAttempt`, `LoadAttempt`, `AttemptHistory`, `ReadCandidate`, `ReadAcceptedMaterial`, `ReadFirstConflict`, `PrepareDispatch`, `BeginUpload`, `BeginSubmission`, `ResolveAttempt`, `FinalizeAttempt`, `PrepareAbandon` and `AbandonAttempt`. Candidate input is already packed snapshot/head bytes and payload; this layer does not read selected files or settings. `ReadCandidate` validates and returns retained bytes only while that attempt or a retained publication owns the payload reference; it does not authorize dispatch. Abandonment releases attempt ownership but does not unlink or overwrite a physical file, and does not guarantee that the abandoned attempt can still retrieve its bytes; an unreferenced file may remain charged and be reused only after validation. `ReadFirstConflict` returns the immutable record for a valid conflict, or a zero value with `present=false` for a valid attempt without one; a missing or corrupt report required by the journal refuses readback.

`BeginUpload` and `BeginSubmission` are local reservation/material APIs. They return payload bytes or the exact candidate batch to a caller and perform no network transfer. The `may-have-submitted` boundary is committed before the submission batch is returned. A `commit_unknown` result returns zero material and fences further preparation/writes until `Load` verifies persisted state or the store is reopened. If readback shows that the submission boundary committed, no submission reauthorization or batch replay is available; if the prior phase persisted, the caller may obtain a fresh proposal after readback. Once submitted, a supplied absence remains unresolved: it is not a retry or abandonment authorization and does not prove provider finality. `FinalizeAttempt` accepts only an exactly current candidate; that confirms the local current view, not historical archive completeness or global freshness.

Attempt admission reserves core and lifecycle-event bounds plus three bounded evidence roles: latest `outcome`, `retirement`, and append-once `first-conflict`. Each evidence body is bounded by the 16 MiB slot ceiling and each stored digest adds 32 bytes; all three bodies and digests count once against metadata and the aggregate `EvidenceBytes` budget. The default aggregate is 128 MiB. Defaults permit one active attempt, up to 1,024 historical attempts, 64 retained points, 64 managed named objects and 1.5 GiB charged custody. These finite local caps can stop admission before protocol capacity; there is no automatic eviction or cleanup. Limits are not raised to make a candidate fit. Admission checks mandatory event and proof shapes before candidate custody, and validates capacity again before reference commit. Supplied repository views and suffix proofs are bounded by count, total bytes, context and evidence-slot limits. A later provider view may exceed the local bounds; it is refused rather than truncated or classified resolved. Logical/file-length limits do not guarantee free disk space, RSS, or power-loss durability.

`AttemptHistory` bounds whole attempt entries by both `HistoryPageEntries` and `HistoryPageBytes`. A lowered byte bound may prevent paging past one oversized aggregate entry: when that entry is first on a requested page, paging returns a capacity-class refusal and no partial page rather than splitting or skipping it. This does not change the separate by-ID `LoadAttempt` and `ReadFirstConflict` APIs; those still perform their own validation and bounds checks. A terminal outcome can remain active when a fresh required view or proof exceeds lowered limits. Retirement requires fresh evidence; a stale view must not be replayed to bypass a current bound.

Candidate payload bytes at this layer are plaintext files in the private `payloads/` child (mode `0700`), with files mode `0600`. New payloads use anonymous `O_TMPFILE` staging and a no-replace link; the file, payload directory and store root are synchronized before any referencing row commits. Registered, shared and valid-orphan reuse follows the same synchronization path. Unsupported anonymous staging or link semantics refuse without a named fallback. A failure before linking leaves no named partial file; a later sync or database failure may leave a complete unreferenced file, which remains charged and is not implicitly removed or repaired. Some candidate-intake inventory or inspection failures use the same coarse `ErrLimit/attempt/capacity` refusal; that does not necessarily mean configured or physical storage is literally full. If a caller later transmits plaintext before a failed or abandoned publication, provider-side copies may remain and local abandonment cannot retract them.

Outcomes are derived from caller-supplied repository membership and the captured candidate/predecessor. Repository origin, revision, policy and other supplied context are caller assertions, not authenticated provider data. After the first durably recorded lost fence, the attempt stores one immutable `first-conflict` envelope linked by a domain-separated ID from its originating `outcome-lost-fence` event. `ResolveAttempt` and direct submitted `AbandonAttempt` can record that first proof transactionally. Later outcome evidence may refresh, but every terminal refresh must extend the previously held suffix as an exact `(key, record bytes)` prefix; a rewind, rewritten descendant or substituted occupant refuses without mutation. The immutable first-conflict record preserves its original head-bound suffix even when the latest outcome advances. `ReadFirstConflict` returns that local structural envelope and head fields after reopen without reading candidate payload bytes; it does not authenticate the evidence, establish provider finality, prove a person saw the conflict, or authorize a keep-local action. Missing or corrupt evidence required by the journal refuses readback. First-conflict bytes and IDs, like other attempt/history evidence, are sensitive and unsuitable for routine logging.

Only one attempt may be active per store. An unresolved submitted attempt can indefinitely block every later attempt. There is no automatic garbage collection, physical cleanup or repair of missing/corrupt payload files. These offline APIs do not authenticate account or repository membership, establish provider atomicity/policy enforcement, or provide a CLI, service, network, provider, installed-path or real-data release claim.

`ReadAcceptedMaterial` returns detached record and payload bytes only for the exact current accepted revision owned by a successfully finalized publication attempt. Position-only `Accept` does not retain incoming payload bytes, even if matching bytes exist as a candidate, catalogued object or orphan. After a `commit_unknown` result, call `Load` or reopen before reading. The method verifies the retained owner and local material and returns either complete detached output or a zero result; it never creates or repairs custody. This proves local byte availability and integrity only, not provider authenticity, global freshness, durable-base eligibility or permission to apply. The schema-3 catalog carries the `accepted_material_refs` table, its migration and its reference validation, but nothing records incoming references yet: an incoming accepted-material owner reader and intake remain unimplemented, so incoming accepted-material retention is not implemented.

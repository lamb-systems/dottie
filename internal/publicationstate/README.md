# Durable local publication positions

The position API in `internal/publicationstate` is an unwired, local-only library for a caller-supplied publication selection, bounded record evidence, a locally accepted position and explicit first-use/replacement consent. It is not provider transport or authentication. The future caller must authenticate account/session/repository membership, current policy and the supplied repository observation before calling this API. The origin binding is a caller-provided association, not proof: this package requires exact `Observation.Origin` equality with its immutable store binding before caching, preparing or accepting. Spaces and public-repository bindings are separate profiles and are never inferred from one another.

The position API is `Open(directory, binding)`, `OpenWithLimits(directory, binding, limits)`, `Close`, `Load`, `RecordObservation`, `Prepare`, `Accept` and bounded `History`. The Open entry points, including `OpenWithOptions`, accept no context and use `context.Background()` internally; they provide no caller-cancellation guarantee. The directory must already exist, be absolute, owned by the current user, and have mode `0700`. Existing lock/database/WAL/SHM objects must already be owned private regular files at `0600`; unsafe objects and hard links where detectable refuse before lock acquisition or SQLite. No path is discovered, directory is created, or permission is repaired. A mode=ro SQLite probe reads committed WAL schema metadata before a read-write connection is opened. The current library SQLite schema is 3: a new or valid initial empty database is created at schema 3, and a healthy current schema-3 database opens ordinarily whether the upgrade permissions are true or false. Ordinary `Open` refuses a recognized schema-1 or schema-2 store with `upgrade_required`; the probe is not a usable read-only store. Only `OpenWithOptions` with both `UpgradeFromPositions` and `UpgradeFromAttempts` enabled upgrades a genuine schema-1 position store directly to schema 3; a genuine schema-2 store requires `UpgradeFromAttempts` alone. Both permissions default to false, and enabled permissions on a new or current database cause no migration.

The upgrade validates the exact source schema, binding, limits and complete stored state before the migration transaction and revalidates them through the actual migration transaction. Before its first write, it also compares the source metadata exactly with the previously captured metadata; the probe and advisory lock are not substitutes for this transaction-local validation. Full source-state validation is distinct from the captured metadata comparison, not a byte snapshot comparison of every source row. A schema-1 upgrade adds the empty attempt tables and indexes, canonical `attempt_limits` and zero `attempt_mutation_revision` metadata, and the empty `accepted_material_refs` table. A schema-2 upgrade adds only the empty `accepted_material_refs` table. Both paths set SQLite `user_version` to 3 in the same migration transaction. Neither rewrites preserved source rows, counters, wire encodings or original limits: the database ID, binding, accepted floor, cache, raw accepted records and historical event encodings remain unchanged. No owner is inferred, no ownership row is backfilled and no candidate payload byte is written.

An upgrade Commit error or a post-Commit Open-completion failure returns a nil Store with `ErrStorage/open/commit_unknown`, requiring explicit reopen and readback; it does not prove rollback. Unknown or committed-with-error upgrade outcomes receive the same classification. Ordinary no-migration refusal classes are unchanged. Foreign, lookalike, active-v1, corrupt and future schemas are not adopted. The lock is advisory on this local filesystem. Malicious same-user namespace replacement and stronger path-opening guarantees are out of scope.

The database holds one immutable account/backend/repository/vault binding and creation-time limits. Reopening with another binding or limits refuses. There is no reset, accepted-history deletion, rebind, automatic migration, installed default path or active executable integration. SQLite uses one connection, a mutex and lifetime flock, WAL, FULL synchronous mode, foreign keys and a bounded busy timeout.

`Prepare` and `Accept` revalidate every supplied record and decode the candidate payload bytes with `publication.DecodePayload`; a prior valid marker never substitutes for those bytes. Payload bytes are not persisted by the position API. A stored floor and audit remain readable without the payload, but preparing/accepting again requires valid supplied payload bytes. Accepted history retains candidate-first descending ancestry references and the raw records needed to verify them; unused supplied records affect only the framed supplied-set digest. The position API does not claim complete repository membership, newest-position freshness, authorship, Spaces privacy, provider behavior, or authenticity.

The private compare-and-swap and consent digests use fixed ordered JSON wire DTOs, `[]byte` standard base64, UTF-8 validation, HTML escaping disabled and strict canonical round trips. They are internal store tokens, not a public or portable pin/confirmation protocol. `Floor.DatabaseID` and `Floor.Generation` must be consumed together as the invalidation pair `(DatabaseID, Generation)`: generation alone repeats after a new database is created. The v2 attempt layer consumes this pair for attempt eligibility and floor-replacement blocking; the service library also consumes it for process-local reconciliation-base eligibility, while durable v2 applied-base and journal integration remain unwired. Spaces remains unwired, and this package does not enable service cutover. See [offline local publication reconciliation](../service/README.md#offline-local-publication-reconciliation) for that separate service-library contract.

The accepted event log is append-only and has a default terminal cap of 8192 events. There is no hidden eviction, reset or new-directory recovery that preserves continuity. Once event count or accepted logical-byte capacity is exhausted, new first-use/advance/replacement events refuse with `ErrLimit/accept/capacity`; `Load`, `History` and fully validated same-position no-ops remain available. The cap is finite and is not an unlimited lifetime or guaranteed replacement reserve. The independent record-only cache has default limits of 4096 records, 1024 observations and 16 MiB logical bytes. Cache saturation refuses only cache intake and never inserts cache rows during `Accept` or gates authoritative capacity. Accepted storage separately caps 16384 unique records and 128 MiB logical bytes.

Logical accounting is deterministic. A cache or accepted record is `raw record byte length + CID byte length + key byte length + 8` for sequence metadata. An observation is its canonical metadata byte length plus 32 bytes for its ID and 8 bytes of row metadata. An event is canonical event-body length, event digest length, stored old/new floor encodings, mode/reason/stop text lengths and 8 bytes for its revision key. Accepted logical bytes sum accepted record and event accounting. History counts each canonical event-body length plus digest/revision metadata and each unique raw-record reference's record accounting once per page; it returns the largest complete prefix that fits 16 MiB without skipping an event. These are logical row/read bounds, not physical SQLite/WAL/index size, disk-space guarantees, RSS bounds or power-loss guarantees.

`Accept` atomically commits accepted raw records, complete event evidence, active floor, revision/generation and the historical payload-validation marker. It has no fallible post-success-commit check. A commit error is returned as `ErrStorage/<stage>/commit_unknown`, the live store refuses further preparation/writes until `Load` verifies persisted floor/audit state or the store is closed and reopened, and callers must read back rather than infer rollback. A successful marker is historical validation evidence, not payload availability. `Open`, `Load`, `Prepare`, `Accept` and `History` currently scan and revalidate the complete bounded accepted audit before proceeding; a History page caps returned event/evidence bytes, not total verification work. `HistoryEvent.Trace` references resolve through the page-level `HistoryPage.Records`, which deduplicates raw records by CID and includes each returned event's held old-floor record when present. Missing/corrupt accepted evidence refuses the page without partial results.

Errors expose only closed class/stage/reason metadata through formatting and unwrap, apart from the forwarded payload-validation families described with `AcceptMaterial`. No raw SQLite/filesystem causes are returned. The position library stores sensitive position and repository/policy context; routine logs should use neither `Floor` nor `History` values.

## Offline publication attempts

The SQLite schema-3 attempt layer shares the local publication-state database and lock, and supports durable attempts and plaintext candidate custody. Its incoming-reference table is validated by full reads, and the accepted-material reader resolves exact-current finalized or incoming owners. SQLite schema version 3 is separate from the unchanged existing attempt encodings and the version-2 publication protocol. It does not replace the position API or wire transport. Its API is `OpenWithOptions`, `PrepareAttempt`, `CreateAttempt`, `ActiveAttempt`, `LoadAttempt`, `AttemptHistory`, `ReadCandidate`, `AcceptMaterial`, `ReadAcceptedMaterial`, `ReadFirstConflict`, `PrepareDispatch`, `BeginUpload`, `BeginSubmission`, `ResolveAttempt`, `FinalizeAttempt`, `PrepareAbandon`, `AbandonAttempt` and `RejectAttempt`. Candidate input is already packed snapshot/head bytes and payload; this layer does not read selected files or settings. `ReadCandidate` validates and returns retained bytes only while that attempt or a retained publication owns the payload reference; it does not authorize dispatch. Abandonment releases attempt ownership but does not unlink or overwrite a physical file, and does not guarantee that the abandoned attempt can still retrieve its bytes; an unreferenced file may remain charged and be reused only after validation. `ReadFirstConflict` returns the immutable record for a valid conflict, or a zero value with `present=false` for a valid attempt without one; a missing or corrupt report required by the journal refuses readback.

`BeginUpload` and `BeginSubmission` are local reservation/material APIs. They return payload bytes or the exact candidate batch to a caller and perform no network transfer. The `may-have-submitted` boundary is committed before the submission batch is returned. A `commit_unknown` result returns zero material and fences further preparation/writes until `Load` verifies persisted state or the store is reopened. If readback shows that the submission boundary committed, no submission reauthorization or batch replay is available; if the prior phase persisted, the caller may obtain a fresh proposal after readback. Once submitted, a supplied absence remains unresolved: it is not a retry or abandonment authorization and does not prove provider finality. `RejectAttempt` is a separate provider-refusal path, not an absence path: it records the terminal `provider-rejected` outcome and retires a `may-have-submitted` attempt whose caller has independently established, outside this store, that the provider refused the submission batch and committed no record. It takes only the attempt identity and its current state digest; it reads no supplied view and needs none, refuses a `prepared`, `upload-started` or already-outcome attempt and a stale token, and releases ownership, the active pointer, pending genesis and reservations like an abandonment. FinalizeAttempt` accepts only an exactly current candidate; that confirms the local current view, not historical archive completeness or global freshness.

Attempt admission reserves core and lifecycle-event bounds plus three bounded evidence roles: latest `outcome`, `retirement`, and append-once `first-conflict`. Each evidence body is bounded by the 16 MiB slot ceiling and each stored digest adds 32 bytes; all three bodies and digests count once against metadata and the aggregate `EvidenceBytes` budget. The default aggregate is 128 MiB. Defaults permit one active attempt, up to 1,024 historical attempts, 64 retained points, 64 managed named objects and 1.5 GiB charged custody. These finite local caps can stop admission before protocol capacity; there is no automatic eviction or cleanup. Limits are not raised to make a candidate fit. Admission checks mandatory event and proof shapes before candidate custody, and validates capacity again before reference commit. Supplied repository views and suffix proofs are bounded by count, total bytes, context and evidence-slot limits. A later provider view may exceed the local bounds; it is refused rather than truncated or classified resolved. Logical/file-length limits do not guarantee free disk space, RSS, or power-loss durability.

`AttemptHistory` bounds whole attempt entries by both `HistoryPageEntries` and `HistoryPageBytes`. A lowered byte bound may prevent paging past one oversized aggregate entry: when that entry is first on a requested page, paging returns a capacity-class refusal and no partial page rather than splitting or skipping it. This does not change the separate by-ID `LoadAttempt` and `ReadFirstConflict` APIs; those still perform their own validation and bounds checks. A terminal outcome can remain active when a fresh required view or proof exceeds lowered limits. Retirement requires fresh evidence; a stale view must not be replayed to bypass a current bound.

Candidate payload bytes at this layer are plaintext files in the private `payloads/` child (mode `0700`), with files mode `0600`. New payloads use anonymous `O_TMPFILE` staging and a no-replace link; the file, payload directory and store root are synchronized before any referencing row commits. Registered, shared and valid-orphan reuse follows the same synchronization path. Unsupported anonymous staging or link semantics refuse without a named fallback. A failure before linking leaves no named partial file; a later sync or database failure may leave a complete unreferenced file, which remains charged and is not implicitly removed or repaired. Some candidate-intake inventory or inspection failures use the same coarse `ErrLimit/attempt/capacity` refusal; that does not necessarily mean configured or physical storage is literally full. If a caller later transmits plaintext before a failed or abandoned publication, provider-side copies may remain and local abandonment cannot retract them.

Outcomes are derived from caller-supplied repository membership and the captured candidate/predecessor. Repository origin, revision, policy and other supplied context are caller assertions, not authenticated provider data. After the first durably recorded lost fence, the attempt stores one immutable `first-conflict` envelope linked by a domain-separated ID from its originating `outcome-lost-fence` event. `ResolveAttempt` and direct submitted `AbandonAttempt` can record that first proof transactionally. Later outcome evidence may refresh, but every terminal refresh must extend the previously held suffix as an exact `(key, record bytes)` prefix; a rewind, rewritten descendant or substituted occupant refuses without mutation. The immutable first-conflict record preserves its original head-bound suffix even when the latest outcome advances. `ReadFirstConflict` returns that local structural envelope and head fields after reopen without reading candidate payload bytes; it does not authenticate the evidence, establish provider finality, prove a person saw the conflict, or authorize a keep-local action. Missing or corrupt evidence required by the journal refuses readback. First-conflict bytes and IDs, like other attempt/history evidence, are sensitive and unsuitable for routine logging.

Only one attempt may be active per store. An unresolved submitted attempt can indefinitely block every later attempt unless a definite provider refusal retires it with `RejectAttempt`; absence still cannot. There is no automatic garbage collection, physical cleanup or repair of missing/corrupt payload files. These offline APIs do not authenticate account or repository membership, establish provider atomicity/policy enforcement, or provide a CLI, service, network, provider, installed-path or real-data release claim.

`ReadAcceptedMaterial` returns detached record and payload bytes only for the exact current accepted revision with either finalized-publication ownership or an exact incoming reference. The public method performs full `readState` validation and exact expected-floor equality before bounded owner lookup, then the existing private-directory/file checks and final context check. Its private owner helper receives the same queryer and stage, acquires no connection and performs no filesystem work; it reuses the finalized-owner audit or the schema-3 incoming-reference validator and record loader. Position-only `Accept` does not create incoming references, even if matching bytes exist as a candidate, catalogued object or orphan. After a `commit_unknown` result, call `Load` or reopen before reading. A graceful close and reopen returns the exact persisted floor, its accepted event and the same reader bytes; that is exact persisted readback, not a crash or power-loss durability claim. The method returns complete detached output or a zero result and never creates or repairs custody. This proves local byte availability and integrity only, not provider authenticity, global freshness, durable-base eligibility or permission to apply. The schema-3 catalog carries the `accepted_material_refs` table, migration and reference validation. `AcceptMaterial(ctx, mode, expectedStateToken, observation, payload, confirmation)` is the public incoming-material producer for caller-supplied packed bytes; it has no CLI or service caller. It reuses the ordinary acceptance transaction for the same modes as `Accept`, returns a detached clone of the accepted floor, and reports every refusal with the zero floor, and with the exception of the pre-transaction input faults below every refusal carries the `accept_material` stage: closed store and context faults, `commit_unknown` while fenced, a defensive `upgrade_required` for a store already known not to be schema 3 (the public openers refuse such a store first), `ErrInvalid/input/mode` for an unrecognised mode and observation or record-set faults, all typed at the `input` stage as `Accept` types them, custody input faults as `record_set`, sidecar preflight as `io`, custody capacity as `ErrLimit/accept_material/capacity`, custody file faults as `material_missing`, `material_unsafe`, `material_corrupt` or `io`, and an existing owner whose bytes differ as `corrupt`. Only when that transaction leaves the accepted revision without an owner does it check custody capacity, persist and catalog the payload, and insert one incoming reference. An existing finalized or incoming owner whose basename, record bytes, blob CID and size all match is a verified no-op; a mismatch refuses as corrupt rather than converting roles, rewriting or deleting. That no-op also reopens or revalidates the private payload directory against any pinned descriptor and reads the persisted owner's selected file against its blob CID, so an absent directory or file refuses `material_missing` and corrupt or unsafe bytes refuse `material_corrupt`/`material_unsafe` instead of reporting success. The bounded read synchronizes nothing and allocates the full payload, because a no-op commits no new row. Attachment creates no accepted event, revision, generation or attempt mutation, and it does no repair, overwrite, unlink or limit increase; a refusal after staging may leave one complete, charged, unreferenced payload file. Intake accepts the same modes as `Accept`, first-use, advance and replace-floor, with the same mode and confirmation refusals typed at `accept_material`; an unrecognized mode refuses as `ErrInvalid/input/mode`. A replace-floor acceptance that blocks an active attempt moves the attempt mutation counter only after the transaction succeeds, so a `commit_unknown` result leaves the in-memory counter unchanged until `Load` or reopen, and `Accept` never attaches even when matching bytes already exist. Its attach-path capacity and inventory refusals are coarse: on that path any custody inventory or inspection failure surfaces as `ErrLimit/accept_material/capacity` or `ErrStorage/accept_material/io`, and does not necessarily mean configured physical storage is full. The existing-owner validation above is more precise than the attach path: it reports `material_missing`, `material_corrupt` or `material_unsafe`, while a replaced, unsafe-mode or unreadable payload directory still surfaces as `ErrStorage/accept_material/io`. Direct test-fixture seeding remains schema-unit coverage, not a producer claim. Two error families are inherited rather than normalized: payload bytes that do not match the accepted record's blob reference, and packed bytes that are referenced correctly but malformed, surface as the existing `publication` and `vault` payload errors exactly as `Prepare` and `Accept` forward them today and are not rewrapped as `publicationstate.Error`, and shared record-insertion helpers inside the acceptance transaction can report the `accept` stage rather than `accept_material`. Every such refusal still returns the zero `Floor`, commits nothing and leaves the accepted floor, history and custody unchanged; a definitive classification of those forwarded families is deferred.

## Apply journal in its own database

`OpenJournal(directory)` opens a second, separate SQLite database `journal.db` with its own lock file `journal.db.lock` in the same private position-state directory. It is not part of the position store, its schema, its inventories or its upgrade paths: the position store stays at schema 3 and no position-store table, row, counter or golden changes. The directory and the five journal paths (`journal.db`, `journal.db.lock`, `journal.db.apply.lock`, `journal.db-wal`, `journal.db-shm`) are validated exactly like the store before and after lock acquisition: the directory must be absolute, clean, owned, `0700` and free of setuid/setgid/sticky bits, and every existing journal object must be an owned private regular `0600` file without symlinks, hard links or unexpected kinds. No directory is created, no mode is repaired and no path is discovered; a `journal.db` is created lazily at `0600`. A foreign or future `journal.db` refuses with `ErrSchema/open/schema`, an unsafe or misconfigured one refuses with `ErrInvalid/journal_open/binding`, and a second open on the same path refuses with `ErrLocked/journal_open/locked`. `Journal.Close` releases the connection, the database and the lock.

The journal database has its own `application_id`, its own schema version 2, its own inventory (`backups`, `journal`, `journal_live` index) and exact text comparison of the three schema statements. No migration exists for it and none is invented. A journal `application_id` at schema version 1 refuses with `ErrSchema/journal_open/upgrade_required`; every other version and every lookalike refuses with `ErrSchema/journal_open/schema`. The database is unreleased — no shipped build has ever created a `journal.db`, and only tests and disposable homes have — so version 2 is finalised in place rather than migrated, version 1 is not upgraded, and any later change to these statements needs a new version. The version-2 `journal` table stores the inspected anchor identity (`anchor_path`, `anchor_device`, `anchor_inode`) next to the journaled destination, because recovery must prove it is observing the same directory before it reads presence or absence, and it stores a `(digest, size, mode)` image for both a present preimage and a present postimage. Mode is part of both images so a `0644`<->`0600` change is distinguishable; a present image with a mode outside `0..0777`, and any mode without its digest and size or without the other mode, is `ErrSchema/journal/corrupt`. This is the only version-2 statement and there is no `ALTER`, compatibility path or backfill, so a `journal.db` written by an earlier unreleased draft whose statement text differs refuses with `ErrSchema/journal_open/schema` exactly like any other lookalike. It is created with `PRAGMA journal_mode=WAL`, `synchronous=FULL`, `foreign_keys=ON` and a bounded busy timeout, on a single connection.

Lock ordering is the only cross-database rule, and it is fixed: position-store lock, then the journal lock and the apply lease, then work. The journal lock is acquired after the position-store lock and never before, and no caller acquires the position-store lock while holding the journal lock. `OpenJournal` performs no position-store work, does not import or open the position store and cannot verify that ordering; it is a caller contract. The two databases are independent files to back up, and no cross-database atomicity is claimed anywhere: each journal intent, backup and completion is a single commit in `journal.db`, admission observes only a caller-supplied floor revision, and the journal is authoritative for apply progress while the position-store floor remains the rollback boundary. A crash can therefore leave a durable journal intent for a mutation the position store never observed.

The apply lease is the second half of that ordering. `AcquireApplyLease(ctx)` takes an exclusive, non-blocking `flock` on `journal.db.apply.lock` in the same directory and returns a lease with `Close`. It refuses `ErrLocked/journal/locked` and returns immediately instead of waiting when another apply holds it, so two invocations sharing one open journal, and two processes on one directory, cannot both resolve interrupted rows, admit, plan or mutate; a reentrant acquisition by the invocation that already holds the lease is refused the same way. The lease is held from before `ResolveInterrupted` through admission, planning, every mutation and every completion, and it is released only after the last journal write. It does not replace the lifetime lock, which continues to refuse a second `OpenJournal`.

The writer API is `AcquireApplyLease`, `BeginJournal`, `CompleteJournal`, `MarkIndeterminate`, `BeginRollback`, `CompleteRollback`, `ResolveIndeterminate`, `CheckAdmission`, `ResolveInterrupted`, `EntryCount` and `BackupBytes`. `LiveJournalRows(directory)` is a read-only count of pending, indeterminate and applied/rollback-pending rows used to warn before local-state deletion; a missing `journal.db` is zero rows and an unreadable or unsafe one returns an error the caller must treat as live. `BeginJournal` commits one `pending`/`apply-pending` row with its backup, or a `NULL` preimage and `NULL` backup for an absent preimage, before the caller mutates anything; an absent preimage is never a zero-length backup row. A preimage or postimage is either a present `(digest, size, mode)` or absence: absence is stored as `NULL` digest, size and mode, so a deletion is journaled like any other mutation, and a present image is never stored as a null digest. Scanner absence is decided by SQL `NULL` itself, never by a byte length: a non-`NULL` digest must be exactly 32 bytes and must carry its own non-negative size and its mode, so a zero-length `BLOB`, a digest without a size or mode and a size without a digest are all `ErrSchema/journal/corrupt` rather than an absence. A correctly encoded present empty file keeps its 32-byte digest and size and mode zero. `BeginJournal` also records the anchor identity, and an intent without an absolute clean anchor path and a non-negative device with a positive inode refuses `ErrInvalid/journal/binding`. The exact state/stage pairs are `pending`/`apply-pending`, `applied`/`apply-complete`, `applied`/`rollback-pending`, `rolled-back`/`rollback-complete`, `failed`/`apply-failed` and `indeterminate`/`indeterminate`; every other stored pair is treated as corrupt. `CompleteJournal` accepts only `pending`/`apply-pending`, requires the observed file to match the recorded postimage exactly — a present file with the recorded digest, size and mode, or a recorded absence observed as absent — and writes `applied`/`apply-complete`; a mismatch refuses `ErrInvalid/journal/journal_observation` and leaves the row pending. `MarkIndeterminate` accepts only `pending`/`apply-pending`. `BeginRollback` accepts only `applied`/`apply-complete` and stages `applied`/`rollback-pending`. `CompleteRollback` accepts only `applied`/`rollback-pending`, requires the observed preimage to match or the recorded absence to be observed, and writes `rolled-back`/`rollback-complete`. `ResolveIndeterminate` is the only exit from `indeterminate`: a postimage match resolves to `applied`, a preimage or recorded-absence match resolves to `failed`, and anything else refuses and leaves the row indeterminate. Every refusal of an edge that is not listed, including a repeated completion, a rollback of a pending row, a rollback completion before `BeginRollback` and a missing entry, is `ErrInvalid/journal/invalid_transition` or `ErrInvalid/journal/journal_entry` and mutates nothing.

Backups live in their own `backups(digest, size, data)` table with digest plus size validation: one backup is capped at 8 MiB, the aggregate charged by the table at 256 MiB and the journal at 4096 rows, and all three refusals are `ErrLimit/journal/capacity` (a single oversized backup refuses before any write). Limits are never raised, no backup and no journal row is ever deleted or pruned automatically, and a digest already stored is reused only after the retained bytes are revalidated inside the intent transaction: the stored size must match, `length(data)` must equal that size inside the 8 MiB bound, and `sha256(data)` must equal the key, so a truncated or same-length-corrupt backup refuses `ErrSchema/journal/corrupt` before any destination is touched. Corruption is never repaired, rewritten or replaced by the caller's bytes; it stays blocking until a human inspects the journal. `BackupBytes` reads the stored bytes back, requires `length(data)` and `size` to agree inside the 8 MiB bound, and refuses `ErrSchema/journal/corrupt` when the digest does not match the bytes. A backup survives reopen and survives its entry reaching `rolled-back`.

`CheckAdmission(ctx, floorRevision)` reads and never mutates. It refuses `ErrContinuity/journal/journal_blocked` with a `*JournalBlockedError` naming the blocking entry and its state, stage and seen floor revision when any live row is `pending`, `indeterminate` or `applied`/`rollback-pending`, and when any live row's `seen_floor_revision` exceeds the supplied floor. `applied`/`apply-complete` rows admit at or above their recorded floor, and `failed` and `rolled-back` rows never block.

`ResolveInterrupted(ctx, observe)` walks the rows that need resolution — `pending`, `indeterminate` and `applied`/`rollback-pending` — asks the caller's `observe(entry)` for each destination's observed digest, size and mode, and applies the same rules: a postimage match resolves to `applied`, a preimage or recorded-absence match resolves to `failed` or `rolled-back`, an undecidable observation becomes or stays `indeterminate`, and an observation error or invalid observation reports `unobserved` and leaves the row unchanged. An interrupted deletion therefore resolves to `applied` when the destination is observed absent and to `failed` when the preimage is still there. The observer receives the whole row, including its recorded anchor path, device and inode, because presence or absence is only meaningful for the directory the intent was written against: the caller must open that anchor through a handle-bound open, verify the handle's identity against the recorded device and inode, and observe the journaled relative destination through that same handle. An anchor that is changed, missing or unsafe is reported as an observation error, so the row stays unchanged and keeps blocking instead of being resolved from another directory's contents; the caller-provided observer is the only party that can perform this open, and a caller that observes by pathname alone voids that guarantee. It returns one `JournalResolution` per visited row, is idempotent, and is not exposed as a command or a flag: no CLI command calls this API today, and the future pull/push caller must call it before `CheckAdmission`. `EntryCount(ctx)` is the read-only total row count used to assert persistence, including terminal `failed` and `rolled-back` rows that recovery and admission no longer visit; it never resolves, mutates or blocks. Crash and power-loss safety of this library is modelled by commit boundaries and injected failure points only, not proven by its own tests; the service apply harness (`TestApplyCrashStagesLeaveARecoverableJournal`) supplies process-death evidence for the apply path, and no power-loss or fsync-completeness evidence is claimed anywhere.

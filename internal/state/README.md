# Local state

The state database and immutable payloads live under `$XDG_STATE_HOME/dottie/`; neither bases nor pending work resolve into `AppCacheDir`. `payloads/` contains files named by their SHA-256 digest. Payloads are written before a row references them. Referenced payloads are retained; explicit retention pruning lists candidates before apply. A payload is deletable only when it has a known recovery-point epoch strictly below the oldest retained boundary, is not associated with a retained recovery point, and is unreferenced by applied bases, outbound intents, conflicts and non-prunable journal backups. A candidate with an unknown epoch or incomplete retained-point inventory is preserved. These checks keep recorded recovery material and local references readable after cache cleanup and restart.

The directory is private (`0700`), and the database, WAL/SHM sidecars and coordinator lock are private (`0600`). The state store owns one SQLite connection and holds `state.db.lock` for its lifetime. The lock is an advisory local-filesystem coordinator lock, not a distributed lock; NFS cross-host exclusion is unsupported.

Migration DDL and its `schema_version` bump run in one transaction. Initial migration 1 does not rebuild tables. A future migration that rebuilds a table must use SQLite's 12-step order: set `foreign_keys=OFF` before `BEGIN`; create and populate the replacement and run `PRAGMA foreign_key_check` inside the transaction; commit; then restore `foreign_keys=ON`. `PRAGMA foreign_keys=OFF` inside a transaction has no effect. Failed migration transactions leave the prior schema version and rows intact. A database newer than the migration set is refused without downgrade.

The schema stores portable target descriptors, full entry keys and fingerprints, and durable payload references for applied bases, outbound intents, conflicts and apply-journal backups. Checkpoint timestamps and record timestamps are caller-supplied Unix seconds. This package provides persistence only; it does not merge, apply, access the network, or read a clock. Credentials, tokens, keys and passwords do not belong in this database or payload API; operational credentials belong in the keyring.

Migration 11 stores authenticated position evidence keyed by vault, epoch and policy digest. It contains exact policy, control and head bytes, the encrypted snapshot envelope bytes, a certificate set sorted by `(device_id, key_id)`, and an optional kit-signed checkpoint position. Administrative objects and certificates are capped at 64 KiB each, the certificate count at 64, and the snapshot at the vault's 384 MiB envelope limit. The store checks structural bindings and size limits, not signatures; callers must re-authenticate evidence on use and it never overrides provider authority. Snapshot plaintext, recipient private keys, signing keys, content keys, kits and tokens are not stored.

## Transition attempts

`transition_attempts` is an append-once durable record created before candidate upload or `applyWrites` for both publication and administrative transition candidates. It stores the snapshot marker collection/rkey, expected DAG-CBOR record CID, candidate blob CID, epoch, lowercase policy digest, outcome, evidence and caller-supplied Unix creation time. It contains no candidate bytes, plaintext or key material. Ordinary publication evidence records a versioned retry disposition before an outcome update so a failed terminal update does not erase the write/retry classification. The outcome and evidence can be updated after a verified reread; `TransitionAttempts` enumerates rows and `TransitionAttemptsByMarker` filters a marker in `created_at,id` order. The marker lookup is an unindexed scan over this small table; there is no index or schema migration for it. Publication recovery still requires the caller to re-supply the same sealed candidate; this table never stores candidate bytes. Migration 2 adds the table without rebuilding existing state.

`vault_checkpoints` stores one row per 32-byte vault identifier: the trusted root anchor fingerprint, control CID and exact authenticated control bytes, epoch-start snapshot CID, epoch sequence, policy digest and caller-supplied recorded-at Unix seconds. It stores no policy, certificates, kit or key material; verification evidence is supplied locally for each check. `PutVaultCheckpoint` permits a higher epoch or an identical position only; a lower epoch or a different control at the same epoch returns `ErrCheckpointBackwards`. A same-position write cannot replace the control bytes or its bound fields. Migration 3 adds this table without rebuilding existing state.

`vault_publication_observations` stores one row per vault with the last authenticated epoch, publication count and snapshot CID observed by this device. A lower epoch or lower same-epoch count is refused; an identical epoch, count, head CID and control CID is idempotent, while a changed snapshot at that count conflicts. Any same-epoch control-CID change returns `ErrVaultPublicationControlReplacement`; the stored control is an immutable observed-position floor. A same-epoch next count requires a different snapshot whose signed `PrevHeadCID` matches the stored snapshot CID; readers that have an envelope also require its `ParentCID` to match, checked in the same transaction. Skipped counts retain the gap refusal, and ancestry mismatches return `ErrPublicationAncestry`. A higher epoch permits a positive mid-epoch count as an unobserved join only when its `PrevControlCID` matches the stored control; a zero-count baseline is checked against the authenticated control snapshot by the caller. Migration 4's existing `head_cid` stores the observed snapshot CID; migration 7 added `control_cid`. A legacy row whose control CID is empty cannot be refreshed by a differing same-epoch read and cannot authorize an epoch advance.

`vault_epoch_first_seen` stores the first authenticated local observation time for each vault and epoch as caller-supplied Unix seconds. Migration 8 creates the table without historical backfill because existing epochs have no recoverable first-seen time. `RecordVaultEpochFirstSeen` uses an insert-only database conflict rule, so repeated reads or a later publication path cannot reset an epoch's clock. Publication preparation refuses when the row is absent; losing local first-seen state therefore requires rotation rather than restarting the age clock.

## Apply journal

Migration 1 already created `apply_journal` with the operation, target identity, expected preimage, intended postimage and durable backup reference. Migration 5 adds `stage`; migration 6 adds the resolved destination directory, relative destination path and directory device/inode identity. These migrations extend the existing journal rather than creating a second table. New apply rows begin as `pending`. `TransitionJournalEntry` allows only `pending` to `applied`, `failed`, `indeterminate` or `rolled-back`, and `applied` to `rolled-back`; it rejects repeated or reversed transitions. A refused conditional rollback records `skipped-newer-edit` as a stage while keeping the row `applied`. Setting work can use the `setting-set`, `setting-reset` and `setting-read-back` stages; settings apply and rollback are not implemented by this package. `JournalEntries`, `JournalEntriesAll` and `PendingJournalEntries` return rows in SQLite `rowid` insertion order so equal timestamps retain durable operation order. Old rows without resolved roots cannot be redirected using current configuration and are indeterminate during recovery. Failed and indeterminate rows retain their backup and setting values. When an eligible GNOME journal backup is detached by `PruneJournalBackupIfEligible`, the same update clears `backup_ref` and the preimage/postimage value type and text fields; other rows keep those values. Verified applied or rolled-back rows are age-pruned after the seven-day backup retention bound; a payload is removed only if no other persisted record refers to it and the recovery-point eligibility checks permit deletion.

The state package exposes pending-entry lookup and distinct referenced-backup usage for the sync engine. Its APIs take caller-supplied times for pruning; it does not read a clock or the filesystem. GNOME reset observations are represented by setting fingerprints with the SHA-256 digest of an empty payload and no value fields. The rollback-material limit is 256 MiB globally until targets have an explicit vault binding. Exceeding the limit is reported to the caller; existing backups are never deleted to make room.

Migration 9 stores each device's current per-vault retention declaration and recovery points, plus immutable prior revisions. The declaration digest binds its policy digest, floor, declaration time and retained `(epoch, snapshot CID)` points. A below-policy floor is persisted and surfaced by the vault declaration API. Migration 10 adds the recovery-point-to-payload/backup association and an inventory-complete marker; declaring a point creates an incomplete marker, and callers must enumerate its material with `SetRetentionRecoveryPointMaterial` before pruning can proceed. Missing or incomplete inventory returns `ErrRetentionRecoveryPointInventoryUnknown`. Pruning requires the selected boundary to be the oldest retained recovery point and match the stored checkpoint's epoch and snapshot CID and the declaration's policy digest; the observed live head must be later. Material associated with any retained point is preserved at every age, and material at or above the boundary is not eligible. The plan reports candidate epochs and eligibility reasons; a candidate with no associated epoch is unclassified and cannot be deleted. A checkpoint pins the boundary but does not prove that every remote blob remains available; downloads are transient. Migration 11 adds authenticated position evidence without rebuilding existing tables. Migration 12 stores a minimal local vault selection `(vault, device_id, recorded_at)` after device keys are safely stored in the keyring. It contains no secrets, anchor or tokens, and refuses duplicate vault selections. Coordinator onboarding import uses the existing schema: one state transaction inserts the selection, successor `vault_checkpoint` and complete authenticated predecessor position; it refuses an existing selection/checkpoint before writing. `AuthenticatedPositionEvidenceAtEpoch` resolves a unique position for an imported checkpoint's first read and refuses ambiguity rather than selecting a fork.

Migration 13 adds append-only authenticated position history keyed by `(vault, epoch, policy_digest, head snapshot CID)` with an ordered certificate child table and optional signed checkpoint position. Every verified read inserts its position idempotently; the existing latest-position table remains the predecessor-read index. Repeated reads of one head do not duplicate history, and conflicting bytes for an existing identity are refused. Existing latest rows remain queryable as legacy positions, but migration cannot recover head versions that earlier upserts overwrote. The bounded local history summary aggregates journal counts by state/stage and applied-base count/latest timestamp/digest without loading item identities, paths, setting values or payloads.

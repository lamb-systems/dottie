# Local state

The state database and immutable payloads live under `$XDG_STATE_HOME/dottie/`; neither bases nor pending work resolve into `AppCacheDir`. `payloads/` contains files named by their SHA-256 digest. Payloads are written before a row references them. Referenced payloads are retained; journal backups are detached only after a verified rollback or expiry of eligible verified material, and a payload is removed only when no other row references the same digest. General unreferenced-payload collection is not implemented. This retention rule keeps stored bases, intents, conflicts and recovery backups readable after cache cleanup and restart.

The directory is private (`0700`), and the database, WAL/SHM sidecars and coordinator lock are private (`0600`). The state store owns one SQLite connection and holds `state.db.lock` for its lifetime. The lock is an advisory local-filesystem coordinator lock, not a distributed lock; NFS cross-host exclusion is unsupported.

Migration DDL and its `schema_version` bump run in one transaction. Initial migration 1 does not rebuild tables. A future migration that rebuilds a table must use SQLite's 12-step order: set `foreign_keys=OFF` before `BEGIN`; create and populate the replacement and run `PRAGMA foreign_key_check` inside the transaction; commit; then restore `foreign_keys=ON`. `PRAGMA foreign_keys=OFF` inside a transaction has no effect. Failed migration transactions leave the prior schema version and rows intact. A database newer than the migration set is refused without downgrade.

The schema stores portable target descriptors, full entry keys and fingerprints, and durable payload references for applied bases, outbound intents, conflicts and apply-journal backups. Checkpoint timestamps and record timestamps are caller-supplied Unix seconds. This package provides persistence only; it does not merge, apply, access the network, or read a clock. Credentials, tokens, keys and passwords do not belong in this database or payload API; operational credentials belong in the keyring.

## Transition attempts

`transition_attempts` is an append-once durable record created before candidate upload or `applyWrites` for both publication and administrative transition candidates. It stores the snapshot marker collection/rkey, expected DAG-CBOR record CID, candidate blob CID, epoch, lowercase policy digest, outcome, evidence and caller-supplied Unix creation time. It contains no candidate bytes, plaintext or key material. The outcome and evidence can be updated after a verified reread; `TransitionAttempts` lets a process restart enumerate unresolved entries and the corresponding publication or transition resolver can verify them without resending a batch. Migration 2 adds the table without rebuilding existing state.

`vault_checkpoints` stores one row per 32-byte vault identifier: the trusted root anchor fingerprint, control CID and exact authenticated control bytes, epoch-start snapshot CID, epoch sequence, policy digest and caller-supplied recorded-at Unix seconds. It stores no policy, certificates, kit or key material; verification evidence is supplied locally for each check. `PutVaultCheckpoint` permits a higher epoch or an identical position only; a lower epoch or a different control at the same epoch returns `ErrCheckpointBackwards`. A same-position write cannot replace the control bytes or its bound fields. Migration 3 adds this table without rebuilding existing state.

`vault_publication_observations` stores one row per vault with the last authenticated epoch, publication count and snapshot CID observed by this device. A lower epoch or lower same-epoch count is refused; an identical count and snapshot is idempotent, while a changed snapshot at that count conflicts. A same-epoch next count requires a different snapshot whose signed `PrevHeadCID` matches the stored snapshot CID; readers that have an envelope also require its `ParentCID` to match, checked in the same transaction. Skipped counts retain the gap refusal, and ancestry mismatches return `ErrPublicationAncestry`. A higher epoch permits a positive mid-epoch count as an unobserved join; a zero-count baseline is checked against the authenticated control snapshot by the caller. Migration 4's existing `head_cid` stores the observed snapshot CID; no migration is needed for ancestry checks.

## Apply journal

Migration 1 already created `apply_journal` with the operation, target identity, expected preimage, intended postimage and durable backup reference. Migration 5 adds `stage`; migration 6 adds the resolved destination directory, relative destination path and directory device/inode identity. These migrations extend the existing journal rather than creating a second table. New apply rows begin as `pending`. `TransitionJournalEntry` allows only `pending` to `applied`, `failed`, `indeterminate` or `rolled-back`, and `applied` to `rolled-back`; it rejects repeated or reversed transitions. A refused conditional rollback records `skipped-newer-edit` as a stage while keeping the row `applied`. Old rows without resolved roots cannot be redirected using current configuration and are indeterminate during recovery. Failed and indeterminate rows retain their backup. Verified applied rows retain their backup for seven days to support user rollback. Verified rollback permits immediate pruning, and age expiry prunes only applied or rolled-back backups; a payload is removed only if no other persisted record refers to it.

The state package exposes pending-entry lookup and distinct referenced-backup usage for the sync engine. Its APIs take caller-supplied times for pruning; it does not read a clock or the filesystem. The rollback-material limit is 256 MiB globally until targets have an explicit vault binding. Exceeding the limit is reported to the caller; existing backups are never deleted to make room.

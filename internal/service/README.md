# Service

The coordinator owns local configuration mutations, state/checkpoint writes, verified reads, preview, restore, base recording and journal recovery. CLI commands provide inputs and render redacted results; they do not call `syncengine.Apply` or modify config/state directly. Target add/remove/mode and `account verify --record` are serialized through coordinator entry points.

Dependencies are explicit ports for configuration, state, file capture, GNOME settings resolution/capture, keyring-backed trust/device keys, account session, remote VaultReader, fenced publisher I/O, clock and apply filesystem. The production remote adapter delegates to the real `atproto.VaultReader`; tests can inject deterministic transports and fake keyring/session ports without bypassing cryptographic verification.

A read requires a local vault selection, anchor and checkpoint. The checkpoint is compared with authenticated remote control state using `vault.VerifyControlState`; only current or verified descendants are eligible for apply. The authenticated position is stored on successful reads. Genesis can be checked from the local anchor/control and authenticated remote policy/certificates; non-genesis reads require local predecessor evidence. No kit-free checkpoint guess or anchor-less read is allowed.

GNOME use derives the allowlist from the stored category set and current matrix, verifies the stored matrix version and key digest, resolves the local schema path and requires exact path equality. Wrong-path, unapproved and stale-base GNOME entries are untracked/refused, never treated as absent. Target identity always includes target ID.

Candidate digests bind the verified remote snapshot, local target policy/selection, observations, reconciliation plan and preview action set. They contain no printed values. Restore recomputes the digest before mutation, enforces local mode, recovers pending journal work, uses `syncengine.Apply`, and records applied bases only for the applied prefix. Syncengine currently has a target-wide file mode policy; a candidate requiring different file modes within one target is refused rather than silently altered.

The Linux `gsettings` gate in `tests/local/manual_restore_linux_test.go` drives the coordinator with a signed genesis-epoch snapshot publication, an in-memory AT Protocol transport, the real `atproto.VaultReader`, state-seeded fixture trust/session/keyring ports, isolated HOME/XDG paths and the real GNOME keyfile backend. It verifies exact file bytes/mode and GNOME present/reset values, journal/base rows, applied status reasons, convergence, review consent refusal, same-size verified candidate change refusal, backup-only, missing prepared roots, GNOME reapproval drift, partial file-apply reporting and distinct base-recording failure. These fixture trust inputs are test trust, not production onboarding. S1b evidence is coordinator-level, with real reader authentication and fixture trust. The foreground CLI/unprivileged execution witness is deferred to the post-S3 acceptance. The gate does not execute CLI restore wiring or prove all cryptographic refusal variants in one coordinator run; unit tests remain the evidence for those lower-level contracts.

`Coordinator.Push`/`Publish` captures each configured target, reconciles it against the persisted applied base and the current verified snapshot, and constructs a complete validated snapshot. Conflicts, blocked or unknown identities and untracked entries refuse publication without exposing content. A snapshot equal to the verified remote state is reported as a no-op without blob upload or record writes. A real publication uses fresh in-memory content-key and nonce material plus fresh recipient wraps, then `vault.PreparePublication` and `atproto.PublishWithRetry`/`CommitPublication`. Publication outcomes remain distinct in the returned coordinator status; queued, starved, stale-predecessor, rejected, superseded or unavailable outcomes do not advance the applied base. Only a verified committed read-back records the new base. Restore-only devices are rejected by vault publisher authority before any remote write. Content keys, publication nonces and ephemeral wrap private keys are never written to keyring or state; only the encrypted snapshot is published, and only non-secret attempt metadata are persisted. Synthetic `atprototest.MemoryPDS` coverage exercises genesis, publish, no-op, changed content, conflicts, queued/ambiguous outcomes, lost-response resolution and restore-only refusal.

`Coordinator.PublishAttestation` accepts a device-signed attestation only for the selected local device, after a verified current/descendant read and signature/context checks. The existing `vaultAttestation` collection is fenced separately from snapshot/head writes; its deterministic key makes an identical publication idempotent, and success requires reread membership, exact record CID and signature verification. V2 attestations enumerate ordered recovery points; publication uses the existing collection and OAuth scope.

`Coordinator.History` returns bounded local journal/applied-base summaries and checkpoint metadata, and optionally performs a verified read to report current remote head, publication count, policy digest, freshness and checkpoint currency. Remote unavailability and authentication expiry are distinct statuses; no contents, values or paths are returned. The CLI escapes control characters at presentation time.

`Coordinator.Export` performs a verified current read without a device key or decryption, authenticates the locally persisted checkpoint with the operator-supplied 32-byte kit, enumerates authenticated schema-v2 retention records, and assembles the current, checkpoint/control ancestry, complete publication-head predecessor chain and retained recovery-point positions. Required snapshot records and ciphertext blobs are fetched by CID and verified before `vault.WriteExportArchive` is called. A missing required position, record, blob, mismatched lineage or v1 count-only attestation with a nonzero count refuses with its known CID and leaves the destination unpublished; required objects are never represented as optional omissions. The kit is neither serialized nor written to state/config/keyring, and coordinator copies are cleared after use. Selection-root checking is derived from the serialized local file selections and resolves symlink aliases before allowing the atomic archive write. The CLI refuses existing outputs unless `--overwrite` is explicit. `ImportExportArchive` invokes `vault.ReadExportArchive` with independently supplied vault, anchor and kit and returns only a contained-position/omission report; it does not mutate configuration, state, checkpoints, bases or preferences. The CLI `import` command is validation-only and never infers the expected vault or anchor from the archive.

Migration 13 preserves append-only authenticated positions keyed by head snapshot CID in addition to the latest-position predecessor index. Export completeness depends on the local machine having retained every required signed publication head. A machine provisioned from an onboarding bundle and only one later read may not have the full history and can refuse export; no head is synthesized or signed to fill that gap. This is a library/service API only, not a CLI or history workflow.

`Coordinator.Enroll` and `Coordinator.Revoke` are root-only administrative APIs. They require a verified current/descendant read, a matching 32-byte recovery kit and the root device keyring material, prepare a fresh successor epoch and use the fenced transition path. Enrollment accepts public newcomer keys and an approval fingerprint; revocation removes the device from successor roles and recipients. A committed status is returned only after a verified read-back matches the committed policy/control; only then is the kit-signed administrative checkpoint persisted and a public onboarding bundle returned. Fence-lost, rejected, superseded, unavailable and unverifiable read-back outcomes do not advance the checkpoint. Revocation does not erase historical decryption capability for keys already delivered.

`ExportOnboarding` re-authenticates the current read, checkpoint and predecessor lineage and returns the signed successor position plus the full public predecessor position. `ImportOnboarding` requires explicit vault and root-anchor inputs, validates the bundle and the local device recipient key before writing, then transactionally persists the selection, successor checkpoint and full predecessor position. The imported checkpoint's first read is restricted to that exact authenticated control; after read-back the current position is stored for ordinary future checkpoint comparison. The bundle carries ciphertext and public signed objects only, never the recovery kit or device private keys. The tagged S2/S3 gate in `tests/local/manual_sync_linux_test.go` composes two isolated machines over a shared synthetic `MemoryPDS`, the real `VaultReader`, real genesis/publication/transition paths, and the real GNOME keyfile backend. It verifies enrollment/import, restore/no-op, authority refusals, revocation, historical decryption, schema-v2 attestation publication, complete archive export/import, missing-blob and identity/kit refusals, and redacted local history output. The gate does not run the full export/import CLI binary sequence. These offline tests do not prove live PDS compatibility or a production desktop session; live PDS is P07/P08.

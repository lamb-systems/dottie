# Service

The coordinator owns local configuration mutations, state/checkpoint writes, verified reads, preview, restore, base recording and journal recovery. CLI commands provide inputs and render redacted results; they do not call `syncengine.Apply` or modify config/state directly. Target add/remove/mode and `account verify --record` are serialized through coordinator entry points.

Explicit dependency ports cover configuration, state, file capture, GNOME settings resolution/capture, keyring-backed trust/device keys, account session, remote VaultReader, fenced publisher I/O, clock and apply filesystem. The production remote adapter delegates to the real `atproto.VaultReader`; tests can inject deterministic transports and fake keyring/session ports without bypassing cryptographic verification.

A read requires a local vault selection, anchor and checkpoint. The coordinator compares the checkpoint with authenticated remote control state using `vault.VerifyControlState`; only current or verified descendants are eligible for apply. Successful reads store the authenticated position. Genesis can be checked from the local anchor/control and authenticated remote policy/certificates; non-genesis reads require local predecessor evidence. No kit-free checkpoint guess or anchor-less read is allowed.

GNOME use derives the allowlist from the stored category set and current matrix, verifies the stored matrix version and key digest, resolves the local schema path and requires exact path equality. Wrong-path, unapproved and stale-base GNOME entries are untracked/refused, never treated as absent. Target identity always includes target ID.

Candidate digests bind the verified remote snapshot, local target policy/selection, observations, reconciliation plan and preview action set. They contain no printed values. Restore recomputes the digest before mutation, enforces local mode, recovers pending journal work, uses `syncengine.Apply`, and records applied bases only for the applied prefix. Syncengine currently has a target-wide file mode policy; a candidate requiring different file modes within one target is refused rather than silently altered.

The Linux `gsettings` gate in `tests/local/manual_restore_linux_test.go` drives the coordinator with a signed genesis-epoch snapshot publication, an in-memory AT Protocol transport, the real `atproto.VaultReader`, state-seeded fixture trust/session/keyring ports, isolated HOME/XDG paths and the real GNOME keyfile backend. It verifies exact file bytes/mode and GNOME present/reset values, journal/base rows, applied status reasons, convergence, review consent refusal, same-size verified candidate change refusal, backup-only, missing prepared roots, GNOME reapproval drift, partial file-apply reporting and distinct base-recording failure. The fixtures supply test trust, not production onboarding. The evidence covers the coordinator with real reader authentication and fixture trust. The foreground CLI/unprivileged execution witness is deferred to a later CLI acceptance. The gate does not execute CLI restore wiring or prove all cryptographic refusal variants in one coordinator run; unit tests remain the evidence for those lower-level contracts.

`Coordinator.Push`/`Publish` captures each configured target, reconciles it against the persisted applied base and the current verified snapshot, and constructs a complete validated snapshot. Conflicts, blocked or unknown identities and untracked entries refuse publication without exposing content. The coordinator reports a snapshot equal to the verified remote state as a no-op, without blob upload or record writes. A real publication uses fresh in-memory content-key and nonce material plus fresh recipient wraps, then `vault.PreparePublication` and `atproto.PublishWithRetry`/`CommitPublication`. Publication outcomes remain distinct in the returned coordinator status; queued, starved, stale-predecessor, rejected, superseded or unavailable outcomes do not advance the applied base. Only a verified committed read-back records the new base. Restore-only devices are rejected by vault publisher authority before any remote write. Content keys, publication nonces and ephemeral wrap private keys are never written to keyring or state; only the encrypted snapshot is published, and only non-secret attempt metadata are persisted. Synthetic `atprototest.MemoryPDS` coverage exercises genesis, publish, no-op, changed content, conflicts, queued/ambiguous outcomes, lost-response resolution and restore-only refusal.

`Coordinator.PublishAttestation` accepts a device-signed attestation only for the selected local device, after a verified current/descendant read and signature/context checks. `PublishRetentionAttestation` builds the signed floor and point list from the current local retention inventory and refuses unknown or incomplete inventory before using the same publication path. The current wire schema cannot encode an unknown status, so the builder refuses any request marked with unknown-epoch material. Applied-base payloads and other local references not associated with an authenticated recovery point intentionally make the inventory unknown and block signed attestation publication, even when each selected point's ciphertext inventory is complete. A verified read or push does not authorize a new classification for those holdings. The existing `vaultAttestation` collection is fenced separately from snapshot/head writes; its deterministic key makes an identical publication idempotent, and success requires reread membership, exact record CID and signature verification. V2 attestations enumerate ordered recovery points; publication uses the existing collection and OAuth scope.

`Coordinator.History` returns bounded local journal/applied-base summaries and checkpoint metadata, and optionally performs a verified read to report current remote head, publication count, policy digest, freshness and checkpoint currency. Remote unavailability and authentication expiry are distinct statuses; no contents, values or paths are returned. The CLI escapes control characters at presentation time.

`Coordinator.PlanPrune` and `ApplyPrune` anchor pruning to the held checkpoint's exact epoch, snapshot CID, policy digest and control CID, require that position to be the oldest declared recovery point, require a strictly later authenticated live epoch and complete revalidated inventories, and delegate all reference selection/deletion to state. The CLI requires explicit `--confirm` for apply. The plan reports the recovery floor (oldest complete inventory), confidentiality floor (oldest surviving known material, including protected backups) and unknown holdings separately. A payload or backup still associated with a retained point is protected at every age; an aged backup associated with a point evicted below the boundary may be pruned; a bound backup with no association and a migrated legacy-unbound backup remain protected. Floors can remain below policy or unknown while staged, orphaned or unknown-epoch payloads survive; the retained-point cap limits selected epochs, not on-disk growth. Pruning is foreground-only: B09 scheduling/automatic GC is outside scope, and no background deletion is wired. Export and onboarding fetch required snapshot bodies by CID through the verified remote reader and refuse if a body is unavailable; evidence records do not cache ciphertext.

`Coordinator.Export` performs a verified current read without a device key or decryption, authenticates the locally persisted checkpoint with the operator-supplied 32-byte kit, enumerates authenticated schema-v2 retention records, and assembles the current, checkpoint/control ancestry, complete publication-head predecessor chain and retained recovery-point positions. Export fetches required snapshot records and ciphertext blobs by CID and verifies them before calling `vault.WriteExportArchive`. A missing required position, record, blob, mismatched lineage or v1 count-only attestation with a nonzero count refuses with its known CID and leaves the destination unpublished; required objects are never represented as optional omissions. The kit is neither serialized nor written to state/config/keyring, and coordinator copies are cleared after use. Selection-root checks use the serialized local file selections and resolve symlink aliases before allowing the atomic archive write. The CLI refuses existing outputs unless `--overwrite` is explicit. `ImportExportArchive` invokes `vault.ReadExportArchive` with independently supplied vault, anchor and kit and returns only a contained-position/omission report; it does not mutate configuration, state, checkpoints, bases or preferences. The CLI `import` command is validation-only and never infers the expected vault or anchor from the archive.

Migration 13 preserves append-only authenticated positions keyed by head snapshot CID in addition to the latest-position predecessor index. Export completeness depends on the local machine having retained every required signed publication head. A machine provisioned from an onboarding bundle and only one later read may not have the full history and can refuse export; no head is synthesized or signed to fill that gap. This is a library/service API only, not a CLI or history workflow.

`Coordinator.Enroll` and `Coordinator.Revoke` are root-only administrative APIs. They require a verified current/descendant read, a matching 32-byte recovery kit and the root device keyring material, prepare a fresh successor epoch and use the fenced transition path. Enrollment accepts public newcomer keys and an approval fingerprint; revocation removes the device from successor roles and recipients. The coordinator returns a committed status only after a verified read-back matches the committed policy/control; only then does it persist the kit-signed administrative checkpoint and return a public onboarding bundle. Fence-lost, rejected, superseded, unavailable and unverifiable read-back outcomes do not advance the checkpoint. Revocation does not erase historical decryption capability for keys already delivered.

`ExportOnboarding` re-authenticates the current read, checkpoint and predecessor lineage and fetches required predecessor snapshot bodies by CID through the verified reader; unavailable bodies refuse the export. `ImportOnboarding` requires explicit vault and root-anchor inputs, validates the bundle and the local device recipient key before writing, fetches required evidence bodies by CID through the verified reader, then transactionally persists the selection, successor checkpoint and full predecessor position. The imported checkpoint's first read is restricted to that exact authenticated control; after read-back the current position is stored for ordinary future checkpoint comparison. The bundle carries ciphertext and public signed objects only, never the recovery kit or device private keys. The tagged S2/S3 gate in `tests/local/manual_sync_linux_test.go` composes two isolated machines over a shared synthetic `MemoryPDS`, the real `VaultReader`, real genesis/publication/transition paths, and the real GNOME keyfile backend. It verifies enrollment/import, restore/no-op, authority refusals, revocation, historical decryption, schema-v2 attestation publication, complete archive export/import, missing-blob and identity/kit refusals, and redacted local history output. The gate does not run the full export/import CLI binary sequence. These offline tests do not prove live PDS compatibility or a production desktop session; live PDS is P07/P08.

## Offline local publication reconciliation

The package-level functions `EstablishLocalReconciliationBase` and `PreviewPublicationTarget` are an unwired library, separate from the `Coordinator` and CLI. `PublicationReconciliationRequest` supplies a caller-opened `publicationstate.Store`, independent binding and complete expected floor, canonical snapshot-record and payload bytes, local configuration and target ID, and a `PublicationLocalContext` created with `NewPublicationLocalContext`. The caller supplies the current record and payload bytes on each operation: this library does not fetch them, authenticate a provider observation, or provide a cross-invocation producer. No coordinator or CLI cutover is wired.

`NewPublicationLocalContext` fixes the caller's platform paths and capture/settings dependencies and gives bases process-local context affinity. Callers control handle lifetime and count, must not retarget those dependencies while handles are live, and must create a new context and explicitly establish a base after changing them. Establishment returns an opaque detached plaintext base only after the selected target matches the accepted snapshot, capture and preview are complete, and every reconciliation decision is unchanged. There is no supported serialization/import API. The base records observed local convergence at an accepted local position; it is not evidence of successful apply, publication, global freshness, durable recovery, a receipt or authorization to mutate files/settings.

A nil base to `PreviewPublicationTarget` requests an explicitly unestablished inspection. A malformed or ineligible supplied base refuses with a zero preview and empty disposition; it never falls back to nil-base inspection. `established` means only that the supplied base passed eligibility. Even a successful preview can be incomplete, conflicting or otherwise non-actionable. For an otherwise eligible base established from a remote tombstone and observed local absence, later remote recreation while the local file remains absent yields an `established` but incomplete preview with a divergence conflict, not a download decision for that file.

Eligibility requires the same binding and nonzero database ID/generation, a base revision no later than the current revision, exact retained accepted-floor/event/raw-record evidence, and the exact current selection in the original process-local context. Equal bytes or sequence values, or equal paths/settings references in a different context, do not establish continuity. An older position may remain eligible within the same audited generation; this is not a global-freshness guarantee.

The full caller-supplied snapshot is bounded and validated before projection/filtering: at most 20,000 entries and 20,000 target descriptors, depth 32, 8 MiB per file, 256 MiB of file content and 16 MiB of counted metadata, including setting types and text. Projection reports wrong-path or unapproved GNOME identities as untracked; establishment and preview block the whole consumer on current or retained untracked projections before capture or reconciliation. Unknown or omitted capture coverage does not become confident absence; completeness depends on the trusted local capture-port contract. GNOME structural and reference checks do not prove native GVariant parsing or schema/range compatibility. Remote configuration cannot grant local path access or settings approval.

For preview, bounded request bytes, configuration, local wrapper and supplied base are copied before the first selection `Resolve` callback. This is a Preview guarantee, not a whole-configuration snapshot performed by establishment; callers must keep establishment inputs and trusted dependencies stable through selection. Selection/config admission separately caps 256 configured targets and 1 MiB of counted text, with at most 64 file exclude patterns and 256 GNOME category/reference entries. The selected base/local/remote-view processing limit is 20,000 distinct union keys and 256 MiB of summed regular-file bytes across those views, charging repeated content occurrences. Filesystem capture separately allows at most 20,000 combined observations and skips, depth 32, 8 MiB per file and 256 MiB total per captured target. These are processing bounds, not global handle-count, lifetime or RSS limits.

Filesystem selection anchors are metadata-only, not retained-descriptor authentication. Inode reuse, torn reads and check-to-use/final-syscall windows remain; caller-opened private stores outside standard protected paths remain the caller's exclusion responsibility. The final whole-floor `Load` check is read consistency, not an atomic fence for a later `Apply`. These operations make no persisted logical publication/base/journal writes, but `Store.Load` performs verified readback, reconciles in-process attempt-mutation state and clears the readback fence; `History` requires that fence already be cleared. This does not claim byte-identical SQLite/WAL state or no observable effect.

The new library does not call `syncengine.Apply` or `RollbackApplied` and grants no write authority. Its offline composition tests explicitly supply roots, policy and postimages to the existing engine; their journal target registration is foreign-key setup, not v1 common-base adoption, and nil retention supplies no v2 recovery binding or cross-store atomicity. `Apply` alone neither authenticates intended candidate bytes nor consults the v2 publication floor. An eligible original base can remain usable after partial application, but the library records no applied prefix and does not advance the base; new establishment still requires observed convergence, and convergence does not repair indeterminate historical journals. The persisted v1 state store and active coordinator behavior remain separate.

Preview omits raw contents but exposes user-controlled names, sizes and unkeyed digests that can confirm guesses. Previews, bases, plans, backups and candidates are sensitive and are not routine-log-safe.

Run `go test -count=1 ./internal/service` for service tests and `go test -count=1 ./tests/local -run '^TestPublicationReconcile'` for the synthetic local composition tests. The projection target's nine default seeds run with ordinary `go test`; bounded exploration is explicit: `GOTOOLCHAIN=local go test ./internal/service -run '^$' -fuzz '^FuzzProjectPublicationSnapshotBoundary$' -fuzztime=30s -parallel=2`. Its fixed synthetic GNOME projection generator limits inputs to 128 KiB, 16 entries and 4 KiB quoted values; it does not exercise native settings compatibility or the consumer barrier. `make fuzz` does not include this target.
